# AIOpsLab Local SLM RCA Evaluation Tracker

## Project objective

Build a simple local-LLM agent that uses AIOpsLab's existing telemetry and evaluation functions to perform cloud-incident root-cause localization. Compare native/raw telemetry against graph-augmented parser evidence while recording accuracy, steps, tokens, latency, tool use, and failures.

## Current architecture

```text
AIOpsLab fault injection and telemetry
        ↓
Native actions: get_traces, get_logs, get_metrics, read_* and submit
        ↓
Local agent using Ollama
        ↓
Baseline: bounded native telemetry
Graph: fresh trace → universal parser → compact evidence context
        ↓
AIOpsLab evaluation and timestamped artifacts
```

The parser/evidence layer is evidence-only. It does not use incident ground truth and does not choose the RCA. The SLM makes the final localization decision.

## Implemented components

### `aiopslab_bridge/`

HTTP bridge around the AIOpsLab orchestrator. It exposes health, problem listing, start, action, submit, and stop operations. It is useful for external agents, but the local evaluation agent uses the native Python orchestrator directly.

### `aiopslab_local_agent/`

- `ollama_client.py` — calls Ollama and records prompt/completion tokens and timing.
- `nemotron_agent.py` — local AIOpsLab agent, live terminal output, action normalization, fresh graph parsing, duplicate-action control, and step-budget notices.
- `run_case.py` — runs one incident in `baseline` or `graph` mode and writes evaluation artifacts.
- `universal_evidence_processor.py` — summarizes repeated parser records without making RCA decisions.

### Evaluation artifacts

- `evaluation_results.csv` — primary cumulative comparison table at repository root.
- `reports/evaluation_results.csv` — compatibility copy.
- `research/test_evaluations/<timestamp>_<condition>_<problem>/` — human-readable report, metadata, parser output, compact context, and evidence manifest.
- `research/local_agent_runs/<session_id>/result.json` — complete agent/environment history and model metrics.

## Run modes

- `--condition baseline` — no parser context; native AIOpsLab telemetry only.
- `--condition graph` — parses the fresh trace generated by that exact run and supplies compact graph evidence to the SLM.
- `AIOPSLAB_CONTEXT_FILE` should remain unset for normal experiments; stale context must never be reused.

## Confirmed experiments

### Hotel reservation misconfiguration

Incident: `misconfig_app_hotel_res-localization-1`.

The parser identified strong neutral evidence:

```text
search emits /geo.Geo/Nearby
68 observed calls
68 responses with 5xx
```

The actual faulty component is `geo`, but both models commonly selected caller services such as `frontend` and `search`. This is a difficult distributed-dependency localization case.

Observed Nemotron results included 0% baseline and 0% graph accuracy. Graph context increased token use without improving localization.

Observed Qwen results included 0% baseline and 0% graph accuracy, with repeated tool calls and, in some runs, no final submission.

### Container kill

Incident: `container_kill-localization`.

Nemotron 4B baseline achieved:

```text
submission: ["geo"]
accuracy: 100%
steps: 3
input tokens: 1,227
output tokens: 38
```

Qwen 7B baseline submitted an empty list and achieved 0%. This shows that Nemotron currently performs better on at least one direct service/container failure, while distributed dependency localization remains difficult.

## Known limitations

- AIOpsLab observer threads sometimes print `trace_api.py` port-forward cleanup warnings. These are noisy but evaluation files are normally saved.
- Large contexts can cause very high cumulative token usage or Ollama timeouts. Full artifacts are preserved, but model-visible evidence must remain compact.
- Qwen and Nemotron may repeat telemetry calls or explore unrelated metrics instead of submitting.
- The current duplicate-action control replaces repeated telemetry calls with metrics; this prevents exact repetition but does not fully control broader tool exploration.
- The baseline condition is currently native telemetry without semantic parser filtering. A future bounded-raw baseline should cap tool responses without changing their meaning.
- Existing historical runs before CSV tracking are not automatically backfilled.

## Issues observed during evaluations

### SLM context pressure

Direct telemetry can be large because logs, traces, metrics, tool descriptions, and previous actions are all included in the conversation. With a large Ollama context setting, cumulative prompt usage became very high. One Qwen run reached approximately 132,152 cumulative input tokens across eight calls. A 256k context configuration also caused Ollama requests to exceed the 300-second client timeout.

Impact: slower evaluation, high token usage, model timeouts, and reduced RCA reliability.

Mitigation: use a 16k–32k Ollama context for normal experiments, keep parser evidence compact, add the graph context only once, and preserve full telemetry separately for audit.

### Repeated and unfocused tool calls

Nemotron and Qwen sometimes repeated `get_traces` or requested the same service logs repeatedly. They also explored unrelated metrics and invented trace paths instead of submitting an answer.

Impact: all available steps can be consumed without an RCA submission.

Mitigation: duplicate-action control, step-budget notices, live action printing, and explicit recording of tool-use failures. These controls do not choose the RCA.

### Distributed dependency confusion

For the hotel-reservation misconfiguration incident, telemetry showed failures emitted by `frontend` and `search`, while the failed operation was `/geo.Geo/Nearby`. Small models often submitted the caller services rather than the remote operation target `geo`.

Impact: graph context was available but localization accuracy remained 0%.

Mitigation: expose neutral emitter-versus-operation mappings and evaluate distributed dependency incidents separately from direct service failures.

### Ollama and model-name failures

Using an unavailable model tag such as `qwen2.5-coder:7b-instruct` produced an Ollama HTTP 404. Large context settings also produced read timeouts.

Impact: no model inference and no valid RCA result.

Mitigation: verify model names with `/api/tags`, record timeout/error runs separately, and do not count them as RCA accuracy results.

### Telemetry and Prometheus failures

Prometheus port-forwarding occasionally stopped while the model was requesting metrics. This produced connection-refused errors on local port 32000. Invalid trace paths were also requested by the model in some runs.

Impact: tool errors and incomplete observations.

Mitigation: classify telemetry failures separately from model reasoning failures and retain the full tool history.

### AIOpsLab observer cleanup warnings

The existing observer sometimes printed `trace_api.py` thread errors such as `NoneType` objects during port-forward cleanup, or left the terminal appearing active after results had already been saved.

Impact: confusing terminal behavior, although evaluation reports were usually written successfully.

Mitigation: verify report and CSV output before treating the run as failed; check for actual leftover port-forward processes.

### Infrastructure lifecycle issues

Chaos Mesh Helm installation sometimes reported that a release name was already in use. Kubernetes API availability also briefly failed between runs.

Impact: interrupted setup or invalid experiments.

Mitigation: verify `kubectl cluster-info` and node readiness before rerunning, and separate setup/recovery failures from RCA metrics.

### Current interpretation

The observed 0% results do not all represent the same failure type. Some are genuine localization errors, while others are tool loops, context overload, model timeouts, invalid model tags, or telemetry failures. The final analysis must report these categories separately.

## Research comparison rules

- Use the same incident, model, maximum steps, and Ollama context setting for baseline and graph conditions.
- Run each condition independently with fresh fault injection and fresh telemetry.
- Do not reuse a parser context from another run.
- Treat infrastructure timeouts and telemetry collection failures separately from RCA failures.
- Report localization accuracy, exact/subset success, steps, input/output tokens, model calls, elapsed time, TTL, tool errors, repeated actions, and submission.

- The parser is successfully reducing model-visible evidence size and preserving the relevant operation-failure summary.
- The difficult hotel incident is not a test of context-window capacity alone; all tested SLMs struggle with multi-hop distributed dependency localization.

- Tool-loop failures, model reasoning failures, parser omissions, Ollama timeouts, and AIOpsLab infrastructure warnings must remain separate categories.
- Recurring Jaeger `trace_api.py` `NoneType.poll()` messages are observer cleanup warnings. Trace collection and reports usually complete despite them.

### Prompt and evidence design principles

- The parser may interpret telemetry schema and aggregate evidence, but must not name the root cause or use incident ground truth.
- The SLM must make the final localization decision.
- Graph context should contain service inventory, dependency relationships, operation mappings, explicit failure summaries, representative evidence, and limitations.
- Full parser output remains available as an audit artifact even when the SLM receives bounded context.
- Baseline and graph comparisons must use the same model, incident, step budget, and Ollama context configuration.

## Thesis report evidence register

This section records the information required to write the final research report. Keep it updated after every implementation change and evaluation.

### Research objective

Evaluate whether a local small language model can localize cloud-incident root causes in AIOpsLab, and whether universal parser-generated evidence improves RCA accuracy, efficiency, and tool-use behaviour compared with native telemetry.

### Experimental conditions

- **Baseline:** the SLM receives AIOpsLab telemetry through the native action loop without semantic parser filtering.
- **Graph:** a fresh trace from the same evaluation run is processed by the universal parser and evidence processor; bounded parser evidence is supplied to the SLM while complete parser artifacts are preserved.
- Both conditions use fresh fault injection, fresh telemetry, identical incident IDs, identical model settings, and the same maximum-step budget.
- Parser output is evidence-only and does not receive ground truth or select the faulty service.

### Independent and dependent variables

- Independent variables: model, incident category, baseline/graph condition, context budget, and maximum steps.
- Primary dependent variable: localization accuracy against AIOpsLab ground truth.
- Secondary dependent variables: exact/subset success, steps, cumulative prompt tokens, completion tokens, model calls, elapsed time, TTL, tool calls, duplicate actions, telemetry calls, submission completion, and timeout/error status.
- Context variables: full parser character count, compact context character count, estimated context tokens, source line count, omitted lines, and parser artifacts preserved.

### RCA evaluation definitions

- **Exact localization:** submitted faulty-service set exactly matches the expected set.
- **Subset success:** submitted set is accepted as a subset by the AIOpsLab evaluator; report separately from exact accuracy.
- **False localization:** a valid submission is made but contains the wrong service or services.
- **No submission:** the model consumes the step budget or fails before submitting.
- **Invalid evaluation:** model/Ollama timeout, unavailable model, telemetry collection failure, Kubernetes setup failure, or unrecoverable infrastructure error prevents a fair RCA measurement.
- **Tool-loop failure:** repeated or unfocused telemetry calls prevent timely submission.

### Failure classification used in analysis

Every unsuccessful run should be assigned one or more categories:

1. Model reasoning/localization error.
2. Emitter-versus-downstream dependency confusion.
3. Tool-use loop or repeated action.
4. No-submission/step-budget exhaustion.
5. Invalid action or formatting failure.
6. Context pressure or excessive cumulative prompt growth.
7. Ollama/model timeout or resource pressure.
8. Parser omission or misleading evidence representation.
9. Telemetry/Prometheus/Jaeger failure.
10. Kubernetes, Helm, or AIOpsLab lifecycle failure.

Do not count invalid infrastructure or model-timeout runs as ordinary 0% RCA results.

### Reproducibility record

For every valid run, preserve:

- problem ID and condition;
- model tag and Ollama endpoint;
- timestamp and session ID;
- maximum steps and context configuration;
- exact system prompt version;
- parser and evidence-processor version;
- `result.json` history;
- human-readable evaluation report;
- parser output, compact context, and evidence manifest;
- cumulative comparison CSV row;
- setup, workload, fault-injection, and recovery status.

### Incident taxonomy for thesis analysis

Group incidents by fault type rather than reporting only aggregate accuracy:

- direct container/pod failure;
- Kubernetes or service configuration error;
- authentication/authorization/database failure;
- service discovery or endpoint failure;
- network loss or network delay;
- resource saturation or high CPU/memory;
- queue or dependency backlog;
- distributed operation-target localization;
- application-specific multi-service failure.

### Current evidence-backed findings

- Direct failures can be easier for a small model than distributed dependency failures. Nemotron achieved 100% on one `container_kill-localization` baseline run while the same model family struggled with the hotel distributed misconfiguration case.
- The parser reduced graph context from approximately 66,000–71,000 source characters to approximately 10,000–12,000 model-visible characters without removing the complete audit artifact.
- Compact context size reduction alone did not improve hotel-case localization; Nemotron, Qwen2.5-Coder, and Phi-4-mini still selected caller services or failed to submit.
- Temporal evidence and service-failure comparisons improve evidence availability, but the evaluated SLMs still show difficulty converting operation-level evidence into downstream-service localization.
- Prompt improvements reduced ambiguity in the instructions but did not reliably prevent repeated tool calls or incorrect submissions; agent-side telemetry metrics are therefore required.
- Qwen3 4B produced an inference timeout under partial CPU/GPU offload and should be analysed as an invalid run rather than an RCA failure.

### Threats to validity

- Small numbers of trials can make model comparisons unstable.
- Hardware load, GPU offload, Ollama model loading, and WSL networking affect latency and timeout behaviour.
- AIOpsLab observer cleanup warnings may add noise without invalidating telemetry.
- Different incidents expose different amounts and quality of telemetry.
- Token counts from Ollama and AIOpsLab are different measurements and must not be combined without labels.
- A single difficult distributed incident cannot represent all cloud incident categories.
- Prompt changes, parser changes, and agent-control changes must be versioned so improvements are not attributed to the wrong component.

### Final report chapter mapping

- **Background:** AIOpsLab, local SLMs, cloud telemetry, and RCA.
- **Methodology:** baseline/graph conditions, parser design, agent loop, hardware, Ollama setup, and evaluation protocol.
- **Parser design:** universal schema handling, evidence aggregation, temporal evidence, context budgeting, and ground-truth separation.
- **Agent design:** native AIOpsLab actions, prompt contract, duplicate handling, decision reminders, and metric collection.
- **Results:** CSV-based accuracy, subset success, tokens, latency, steps, tool behaviour, and incident-category breakdown.
- **Error analysis:** model reasoning, tool loops, context pressure, timeouts, parser limitations, and infrastructure failures.
- **Threats and limitations:** reproducibility, hardware, sample size, telemetry quality, and generalization.
- **Conclusion:** whether structured evidence improved efficiency, accuracy, or reliability for the evaluated SLM and incident categories.
